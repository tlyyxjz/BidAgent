## 一、项目定位

### 1.1 一句话定位

面向**供应链金融贷前尽调**与企业采购核验的可验证招投标数据引擎——将不可核验的 LLM 输出转化为可复核、可追踪的数据资产。

### 1.2 目标用户与核心任务

**核心用户**：供应链金融贷前尽调人员

**核心任务**：在审核供应商公开经营活动时，快速核验企业近期中标项目、金额、采购人及原始公告证据。

**系统定位**：BidAgent 位于金融风控的数据准备与事实核验环节，为后续人工尽调或其他风控系统提供带证据的招投标数据，而非直接替代风控决策。

### 1.3 解决的核心问题

金融机构、企业采购部门及市场分析人员在使用招投标数据时，通常面临三个问题：

**信息分散**
政府采购、公共资源交易等平台相互独立，人工跨平台检索和整理成本较高。

**抽取结果不稳定**
LLM 可以提升结构化抽取效率，但可能出现字段错配、金额类型混淆、实体误认及无依据输出。

**缺少可验证证据链**
传统 AI 抽取结果通常只返回字段值，无法说明该结果来自哪一版本公告、哪段原文以及经过了何种校验。

### 1.4 核心差异化

BidAgent 不以平台数量和数据总量作为 MVP 的主要竞争指标，而聚焦以下能力：

- 每个字段可绑定多段原文证据，区分主证据、限定条件和推导输入
- LLM 只生成字段和证据候选，确定性程序负责验证
- 区分项目、公告、来源页面和页面版本四层实体
- 区分官方原始发布、官方转载、商业转载和索引页面
- 识别同源转载，避免将转载数量误判为独立交叉验证
- 将抽取支持度、来源质量和交叉验证状态独立保存
- 使用独立金标测试集验证准确率、覆盖率和无依据输出率
- 只输出可解释的公开招投标活动观察信号，不输出信用评分

### 1.5 适用场景

- **供应链金融辅助尽调**：核查供应商公开中标活动和相关公告证据
- **企业采购管理**：供应商背景核验、中标结果交叉检查
- **市场与竞品分析**：跟踪公开中标记录、采购人分布和区域分布
- **数据系统集成**：通过 API 提供带来源和证据的结构化招投标字段

### 1.6 明确边界

BidAgent：

- 不是招投标全网搜索平台
- 不是企业信用评级系统
- 不直接输出授信或投资建议
- 不依据公开共现数据判断围标
- 不承诺覆盖企业全部投标或中标活动
- 不将模型自报概率直接作为可信度
- 不绕过验证码、付费墙或平台技术限制
- 不替代工商、司法和财务尽调

## 二、MVP 成功标准

BidAgent MVP 是否成功，不以功能数量判断，而以以下五项结果判断：

1. 能从两个已冻结的官方来源适配器采集并处理真实公告
2. 能对核心字段返回经过程序验证的原文证据（支持多段证据）
3. 能区分同一项目的不同公告、同一公告的不同来源和不同版本
4. 能在独立测试集上证明可信管道相对直接 LLM 抽取降低了无依据输出
5. 能通过 Web Demo 展示「字段—证据—来源—版本」的完整追溯链

### 2.1 MVP 必做范围

- 两个已冻结页面体系的官方来源适配器
- 招标公告、中标公告和更正公告
- 六类核心结构化字段
- 字段级多证据验证
- 页面快照与版本管理
- 同源转载识别
- 三维质量评估
- 独立金标评测（含消融实验）
- Web Demo
- REST API
- 基础组织实体公开活动画像

### 2.2 MVP 选做范围

- 废标公告解析
- 关键事实列表
- 供应商高频共现提示
- Word 报告
- 邮件和 Webhook
- 商业平台接入
- 标准化品类价格偏离提示

### 2.3 MVP 暂不实施

- 企业信用评分
- 授信建议
- 中标概率预测
- 围标自动判定
- 全品类 BOQ 异常检测
- 分布式采集
- 图数据库
- 多租户系统
- 商业平台账号池及验证码自动处理
- PDF/OCR 深度解析

## 四、核心数据模型

### 4.1 数据模型总览

BidAgent 使用四层业务模型，并增加组织实体、参与关系和事实断言等辅助模型。

```
TenderProject（采购项目）
    └── TenderNotice（业务公告）
            ├── NoticeParticipant（公告参与关系）
            └── NoticeSource（来源页面）
                    └── NoticeVersion（抓取版本）
                            └── ExtractedField（抽取字段）
                                    └── FieldEvidenceLink
                                            └── Evidence（字段证据）
```

**辅助实体**：
- Organization（组织机构，法律实体属性）
- NoticeParticipant（公告参与关系，业务角色）
- ProjectIdentifier（项目标识）
- FactAssertionKey（事实断言键）

**主键原则**
所有核心实体使用无业务含义的内部稳定主键，推荐使用 ULID。

业务编号、URL 和标题哈希只能作为：
- 外部标识
- 匹配证据
- 去重特征
- 实体归并依据

不得直接将项目编号哈希作为永恒不变的唯一主键。

### 4.2 采购项目 TenderProject

表示贯穿招标、中标、更正、合同等阶段的同一个采购项目。

| 字段 | 类型 | 说明 |
|---|---|---|
| `project_id` | ULID | 内部稳定主键 |
| `canonical_name` | string | 归一化项目名称 |
| `industry_category` | enum | goods / service / engineering / other |
| `purchaser_entity_id` | string/null | 采购人组织实体（主） |
| `agency_entity_id` | string/null | 代理机构实体 |
| `resolution_status` | enum | resolved / ambiguous / unresolved |
| `created_at` | datetime | 首次发现时间 |
| `updated_at` | datetime | 最后更新时间 |

**项目标识 ProjectIdentifier**

同一项目可能存在采购编号、代理编号和内部编号，因此单独建立标识表。

| 字段 | 说明 |
|---|---|
| `identifier_id` | 标识记录 ID |
| `project_id` | 所属项目 |
| `identifier_type` | procurement / agency / platform / lot / other |
| `raw_value` | 原始编号 |
| `normalized_value` | 归一化编号 |
| `issuing_body` | 编号发布主体 |
| `source_id` | 该编号来源页面 |

**项目归并依据**

项目关联采用组合证据，不依赖单一编号：
- 项目编号
- 项目名称相似度
- 采购人
- 代理机构
- 发布时间
- 分包信息
- 官方来源关联
- 公告中明确的前序或后续公告链接

无法确定时应保留为不同项目并标记待消歧，不得强制归并。

### 4.3 业务公告 TenderNotice

表示项目生命周期中的一次业务公告。

| 字段 | 类型 | 说明 |
|---|---|---|
| `notice_id` | ULID | 内部主键 |
| `project_id` | string | 所属项目 |
| `notice_type` | enum | tender / correction / clarification / award / cancellation / contract / other |
| `canonical_title` | string | 归一化标题 |
| `publish_date` | date/null | 发布日期 |
| `effective_date` | date/null | 业务生效日期 |
| `status` | enum | active / superseded / withdrawn |
| `superseded_by` | string/null | 后续替代公告 |
| `created_at` | datetime | 创建时间 |

同一项目的招标金额、中标金额和合同金额属于不同业务事实，不构成冲突。

更正公告覆盖原公告时，应记录：
- 原公告
- 更正公告
- 被修改字段
- 生效时间
- 替代关系

### 4.4 组织实体 Organization

采购人、代理机构、中标人和供应商统一使用组织实体表示。**Organization 只保存组织自身的法律实体属性，不保存业务角色。**

| 字段 | 类型 | 说明 |
|---|---|---|
| `organization_id` | ULID | 内部主键 |
| `canonical_name` | string | 规范名称 |
| `unified_social_credit_code` | string/null | 统一社会信用代码 |
| `aliases` | array | 观察到的别名 |
| `legal_entity_type` | enum | company / government_agency / public_institution / social_organization / individual_business / other / unknown |
| `resolution_status` | enum | resolved / ambiguous / unresolved |
| `resolution_method` | string | 消歧依据 |

**企业名称处理原则**：
- 去除法律后缀的结果仅用于候选召回，不能直接用于实体合并
- 实体合并需要统一社会信用代码或多特征支持
- 无法确定时标记 `ambiguous`

### 4.5 公告参与关系 NoticeParticipant

记录组织在具体公告中扮演的业务角色。同一个组织在不同项目中可能是采购人、供应商或联合体成员。

| 字段 | 类型 | 说明 |
|---|---|---|
| `participant_id` | ULID | 关系 ID |
| `notice_id` | string | 所属公告 |
| `version_id` | string/null | 来源版本，必要时记录 |
| `organization_id` | string/null | 关联的组织实体（消歧后） |
| `raw_name` | string | 原文名称 |
| `normalized_name` | string | 规范化名称 |
| `participant_role` | enum | purchaser / procuring_agency / bidder / winner / consortium_member / subcontractor / other |
| `lot_id` | string/null | 所属分包 |
| `resolution_status` | enum | resolved / ambiguous / unresolved |
| `evidence_id` | string/null | 角色判定的原文证据 |

**供应商画像定义**：组织实体在 bidder、winner 等角色下的公开活动画像。

### 4.6 来源页面 NoticeSource

表示某一公告在具体平台上的页面实例。

| 字段 | 类型 | 说明 |
|---|---|---|
| `notice_source_id` | ULID | 来源页面 ID |
| `notice_id` | string | 所属公告 |
| `source_url` | string | 页面 URL |
| `source_platform` | string | 平台标识（适配器名） |
| `platform_type` | enum | government / authorized / commercial / unknown |
| `publication_role` | enum | original / official_repost / commercial_repost / index_only / unknown |
| `source_quality` | enum | official_original / official_repost / authorized_original / commercial_repost / index_only / unknown |
| `quality_reason` | string | 来源质量判定依据 |
| `origin_url` | string/null | 可识别的原始页面 |
| `repost_of` | string/null | 对应原始来源页面 |
| `source_group` | string | 来源谱系组 |
| `first_seen_at` | datetime | 首次发现时间 |

**来源质量原则**

来源质量保存为可解释类别，不使用没有校准依据的数值评分。

平台类型只是基础信息，最终来源质量必须结合页面级证据判定。

### 4.7 公告版本 NoticeVersion

表示同一来源页面在某一抓取时间的内容状态。

| 字段 | 类型 | 说明 |
|---|---|---|
| `version_id` | ULID | 版本 ID |
| `notice_source_id` | string | 来源页面 ID |
| `fetched_at` | datetime | 抓取时间 |
| `http_status` | integer | HTTP 状态码 |
| `content_sha256` | string | 页面内容哈希 |
| `raw_text_sha256` | string | 清洗后原始纯文本哈希 |
| `normalized_text_sha256` | string | 规范化文本哈希 |
| `previous_version_id` | string/null | 前一个版本 |
| `change_type` | enum | initial / none / minor / material / withdrawn |
| `snapshot_path` | string | 快照存储位置 |
| `normalizer_version` | string | 文本规范化规则版本 |
| `extractor_version` | string | 抽取器版本 |
| `model_identifier` | string | 模型标识 |
| `prompt_hash` | string | 提示词哈希 |

**版本变更原则**
- 页面更新不能覆盖历史版本
- 内容未变化时可只更新检查记录
- 业务字段变化应标记为 material
- 页面删除或公告撤回应记录状态，不直接删除历史事实
- 对外删除请求按数据保留和合规策略处理

### 4.8 抽取字段 ExtractedField

| 字段 | 类型 | 说明 |
|---|---|---|
| `field_id` | ULID | 字段记录 ID |
| `version_id` | string | 来源公告版本 |
| `field_name` | string | 字段名称 |
| `field_type` | enum | amount / date / organization / identifier / fact / text |
| `semantic_role` | string | 字段业务语义角色 |
| `raw_value` | string/null | 模型输出的原始值 |
| `normalized_value` | string/null | 归一化结果（单值主值） |
| `value_count` | integer | 值的数量（多值字段 > 1） |
| `amount_type` | enum/null | budget / ceiling / award / contract / unit_price |
| `lot_id` | string/null | 分包 ID |
| `currency` | string/null | 币种 |
| `tax_status` | enum/null | included / excluded / unknown |
| `support_level` | enum | direct / equivalent / inferred / unsupported / contradicted |
| `support_reason` | string | 判定原因 |
| `cross_verify_status` | enum | independent / consistent_unknown / same_origin / version_difference / conflict / single_source |
| `source_quality_snapshot` | enum | 抽取时来源质量 |
| `primary_evidence_id` | string/null | 主证据（用于快速展示） |
| `display_grade` | enum | high / review / low |
| `display_rule_version` | string | 展示等级规则版本 |
| `created_at` | datetime | 创建时间 |

**展示等级存储原则**

`display_grade` 不是底层事实，而是基于三个质量维度生成的派生结果。

数据库可以缓存该结果用于查询和展示，但必须：
- 保存规则版本
- 支持重新计算
- 不覆盖原始质量维度
- 规则变化后可批量刷新

### 4.9 字段证据关联 FieldEvidenceLink

一个抽取字段可对应多段证据，通过关联表管理。

| 字段 | 类型 | 说明 |
|---|---|---|
| `link_id` | ULID | 关联 ID |
| `field_id` | string | 抽取字段 ID |
| `evidence_id` | string | 证据对象 ID |
| `evidence_role` | enum | primary / context / qualifier / derivation_input / contradiction |
| `sequence` | integer | 展示顺序 |
| `is_required` | boolean | 是否为判定该字段所必需 |

**证据角色说明**：

| 角色 | 含义 |
|---|---|
| `primary` | 直接支持字段值的主证据 |
| `context` | 补充上下文，帮助理解 |
| `qualifier` | 说明分包、金额类型、税率等限定条件 |
| `derivation_input` | 推导计算的输入证据 |
| `contradiction` | 证明字段冲突的原文 |

### 4.10 证据对象 Evidence

| 字段 | 类型 | 说明 |
|---|---|---|
| `evidence_id` | ULID | 证据 ID |
| `version_id` | string | 所属公告版本 |
| `evidence_text` | string | 证据原文片段 |
| `context_before` | string | 前文上下文 |
| `context_after` | string | 后文上下文 |
| `offset_space` | string | 坐标空间：clean_raw_text |
| `raw_start` | integer | 清洗后原始文本起始偏移 |
| `raw_end` | integer | 清洗后原始文本结束偏移 |
| `normalized_start` | integer | 规范化文本起始偏移 |
| `normalized_end` | integer | 规范化文本结束偏移 |
| `section_title` | string/null | 所属章节标题 |
| `match_method` | string | 匹配方法 |
| `normalization_version` | string | 规范化规则版本 |
| `snapshot_sha256` | string | 快照哈希 |
| `raw_text_sha256` | string | 原始文本哈希 |
| `verified` | boolean | 是否经过程序验证 |
| `verification_rule` | string/null | 验证规则版本 |
| `created_at` | datetime | 创建时间 |

**偏移量映射原则**：
- 文本清洗和规范化可能改变字符长度，因此建立双坐标映射
- `normalized_character_index → clean_raw_text_character_index`
- MVP 前端统一在清洗后的原始纯文本快照中进行证据高亮
- 不依赖实时网页 DOM，避免页面变化导致偏移失效

## 五、数据来源与合规采集

### 5.1 MVP 已冻结数据源适配器

MVP 完成两个已冻结页面体系的采集适配器，**不承诺覆盖全国所有地方公共资源交易子平台**。

| 适配器标识 | 平台 | 平台类型 | MVP 状态 | 说明 |
|---|---|---|---|---|
| `ccgp` | 中国政府采购网 | government | 必做 | 国家级政府采购公开公告栏目 |
| `ggzy_national` | 全国公共资源交易平台（国家级） | government | 必做 | 国家级平台检索和公告详情页 |

**适配器冻结范围**：
- 公告类型：招标公告、中标公告、更正公告
- 处理范围：页面正文（HTML），附件仅下载不深度解析
- 索引页 vs 详情页：列表页仅作索引抓取，详情页视为内容来源
- 原始来源判定：以发布主体和页面标注为准

**后续扩展（非 MVP）**：
- 可选择一个结构稳定的区域平台作为补充适配器
- 地方平台结构差异较大，逐个适配，不做"全覆盖"承诺

### 5.2 合规原则

- 优先使用公开 API、开放数据和无需登录的公开页面
- 检查 robots.txt、服务条款及数据使用限制
- 用户提供账号不等于平台授权自动化采集
- 商业平台仅在平台条款、接口协议或其他授权依据允许时接入
- 不绕过付费墙、验证码或访问控制
- 触发验证码、403 或封禁时停止访问，不进行规避
- 采用缓存和条件请求降低重复访问
- 保存来源链接及抓取时间
- 建立来源白名单和下架处理机制
- 商业平台全文默认不随开源仓库发布

### 5.3 采集组件

| 组件 | 职责 |
|---|---|
| `collector.py` | 采集任务调度和部分成功处理 |
| `http_fetcher.py` | 普通 HTTP 页面获取 |
| `browser_renderer.py` | 必要时进行 JavaScript 页面渲染 |
| `rate_limiter.py` | 域名级频率限制 |
| `cache_manager.py` | ETag、Last-Modified 和内容缓存 |
| `snapshot_manager.py` | 快照、哈希和版本管理 |
| `template_monitor.py` | 页面结构变更检测 |

具体请求频率根据平台规则、接口限制、响应状态、缓存命中率和实际业务必要性，进行来源级配置。

## 六、可验证抽取引擎

### 6.1 工作流程

```
公告版本
  → 文本清洗
  → 建立原始文本与规范化文本字符映射
  → LLM 输出字段值和候选证据列表
  → 程序逐段搜索候选证据
  → 确定性字段校验
  → 生成多证据对象（区分角色）
  → 来源质量判定
  → 同源转载和跨源比较
  → 生成三个独立质量维度
  → 根据版本化规则生成展示等级
```

**核心原则**：
LLM 负责提出字段及证据候选，程序负责确认候选是否真实存在并验证其是否支持字段值。

### 6.2 抽取支持度

| 等级 | 说明 | 默认处理 |
|---|---|---|
| `direct` | 原文直接出现，可准确定位 | 可进入高可信 |
| `equivalent` | 经过确定性变换后与原文等价 | 可进入高可信 |
| `inferred` | 通过计算、聚合或语义推导得到 | 待复核，展示推导过程和全部输入证据 |
| `unsupported` | 原文中找不到支持信息 | 默认过滤 |
| `contradicted` | 输出与原文明确冲突 | 默认过滤并记录冲突证据 |

**确定性等价变换示例**
- 中文金额转阿拉伯数字
- 万元转元
- 日期格式统一
- 全角字符转半角
- 英文字母大小写统一
- 项目编号空格和连接符规范化

**推导结果要求**

推导结果必须保存：
- 全部输入证据（通过 derivation_input 角色关联）
- 推导规则
- 中间计算
- 输出结果
- 规则版本

推导结果不得冒充原文直接证据。

### 6.3 来源质量

来源质量由以下两个维度共同判定：

**平台类型**
- government
- authorized
- commercial
- unknown

**页面发布角色**
- original
- official_repost
- commercial_repost
- index_only
- unknown

最终保存可解释类别，不使用未经校准的数值打分。

来源质量的判断依据应包括：
- 页面所属机构
- 页面来源标注
- 原始链接
- 发布时间关系
- 页面正文完整性
- 是否仅提供索引
- 是否能追溯到上游公告

### 6.4 交叉验证状态

| 状态 | 说明 |
|---|---|
| `independent` | 已有证据确认两个业务来源相互独立且事实一致 |
| `consistent_unknown` | 不同页面值一致，但无法证明来源独立 |
| `same_origin` | 多个页面属于同一转载链 |
| `version_difference` | 同一公告不同版本存在正常差异 |
| `conflict` | 相同事实语义和有效时间下出现矛盾 |
| `single_source` | 只有一个可用来源 |

**重要原则**

单一官方原始来源加直接原文证据，本身可以构成高可信字段。

独立跨源验证是增强证据，不是所有公告达到高可信的必要条件。现实中大量公告只有一个业务原始发布主体。

### 6.5 事实断言键

跨源比较不能只比较字段名称和值，必须确保双方表达的是同一业务事实。

每个可比较字段生成 `FactAssertionKey`：

| 字段 | 说明 |
|---|---|
| `project_id` | 所属项目 |
| `notice_type` | 公告类型 |
| `field_name` | 字段名 |
| `semantic_role` | 企业或字段业务角色 |
| `amount_type` | 金额类型 |
| `lot_id` | 分包 |
| `effective_time` | 事实有效时间 |
| `entity_role` | 采购人、中标人、代理机构等 |

只有断言键兼容的记录才能被判断为：
- 一致
- 版本差异
- 事实冲突

预算金额不能与中标金额比较，第一包金额不能与第二包金额比较。

### 6.6 展示等级

| 展示等级 | 默认规则 |
|---|---|
| **高可信** | 直接证据或确定性等价变换，且来源不是未知/索引；不存在事实冲突 |
| **待复核** | 推导结果、商业转载、来源独立性未知或仅有转载链支持 |
| **低可信** | 无证据、原文冲突、来源未知或存在事实冲突 |

最终规则由校准集确定，并保存规则版本。

展示等级只用于降低用户认知成本，三个原始质量维度必须支持展开查看。

## 七、字段规范与归一化

### 7.1 MVP 正式评测字段

正式主评测聚焦六类结构化字段：
1. 项目编号
2. 采购人名称
3. 中标人名称
4. 金额及金额类型
5. 发布日期
6. 投标截止日期

「关键事实列表」作为 Demo 或附加实验，不计入核心验收指标。

### 7.2 多金额模型

同一公告可能同时包含：
- 预算金额
- 最高限价
- 中标金额
- 合同金额
- 单价
- 不同分包金额

金额对象必须保存：

```json
{
  "amount_type": "award",
  "lot_id": "包2",
  "raw_value": "128.50万元",
  "normalized_value": "1285000.00",
  "currency": "CNY",
  "original_unit": "万元",
  "tax_status": "unknown",
  "display_precision": "0.01万元"
}
```

### 7.3 金额正确性判定

字段抽取评测不采用固定百分比容差。

金额是否正确应由原文显示精度决定：
- 金额类型一致
- 分包一致
- 币种一致
- 归一化数值一致
- 仅允许由原始显示精度造成的舍入误差
- 最大允许误差不超过原文最小显示单位的一半

例如原文精确到 0.01 万元，则允许误差由该显示精度决定，不因总金额增大而放宽。

### 7.4 多值字段规则

以下字段可能有多个值：
- 多个中标人
- 联合体成员
- 多个分包金额
- 多个项目编号
- 多个投标截止日期

标注和存储统一采用数组形式，不强行压成一个字符串。

评测时对多值字段使用**集合级 Precision、Recall 和 F1**。

## 八、同源转载和版本识别

### 8.1 识别特征

转载识别使用多特征组合：
- 原始链接
- 页面来源标注
- 项目编号
- 公告类型
- 标题相似度
- 正文 SimHash
- 发布主体
- 发布时间关系
- 附件链接
- 正文中的上游来源说明

### 8.2 判定结果

- 明确原始页面
- 明确官方转载
- 明确商业转载
- 疑似同源
- 独立性未知
- 确认独立来源

SimHash 只能提供候选，不能单独决定来源谱系。

### 8.3 去重原则

- 同一来源页面的相同内容：版本去重
- 同一公告的多个转载：归入同一公告和来源谱系
- 同一项目的不同业务公告：不得去重
- 更正公告与原公告：建立替代关系，不得删除
- 相似但无法确认的页面：保留并标记待判断

### 9.2 MVP 信号

集中度使用：

- 包含投标人名单的公告数量
- 企业消歧状态
- 可能的遗漏
- 信号计算口径

## 十、金标评测体系

### 10.1 数据集规模与统计口径

MVP 推荐 300～350 篇公告，同时报告项目数量。

| 数据集 | 公告数量建议 | 项目数量目标 | 用途 |
|---|---|---|---|
| 开发集 | 130～140 | 约 90 个 | 提示词、规则及代码开发 |
| 校准集 | 80～100 | 约 50 个 | 确定展示等级规则和匹配参数 |
| 测试集 | 100～110 | ≥ 70 个 | 最终独立评测 |

测试集项目数不足 70 个时，应如实报告并说明统计效力限制。

每个数据集同时报告：公告数量、项目数量、来源页面数量、版本数量、字段总数、字段为空数量。

### 10.2 划分原则

- 按采购项目分组切分
- 同一项目的公告、转载和版本进入同一子集
- 测试集在规则冻结前不得用于调参
- 测试结果不得用于本轮系统优化
- 如因非算法性故障重跑，需记录原因
- 可增加时间外测试作为附加实验

### 10.3 金标字段状态

每个金标字段必须标注状态，用于正确计算覆盖率和空值误报率。

| 状态 | 含义 | 是否计入主评测分母 |
|---|---|---|
| `present` | 正文中明确存在 | ✅ 是 |
| `absent` | 应用上可能存在，但当前可见内容中没有 | ✅ 是（用于空值误报率） |
| `not_applicable` | 对该公告类型不适用 | ❌ 否，单独统计 |
| `ambiguous` | 原文存在多个无法确定的候选值 | ❌ 否，单独统计 |
| `attachment_only` | 正文没有，但附件中可能存在 | ❌ 否，单独统计 |
| `unreadable` | 扫描、乱码等原因无法判定 | ❌ 否，单独统计 |

**覆盖率分母修正**：
- 主覆盖率 = 系统正确输出的可评测字段数 / 金标中状态为 `present` 的字段总数
- `not_applicable`、`attachment_only`、`unreadable` 默认不进入主评测分母，单独统计

### 10.4 标注流程

**开发集和校准集**
可使用系统预标注提高效率，再由人工确认和修正。

**测试集**
为降低锚定偏差：
- 至少一名标注者从空白文本开始标注
- 尽量不展示系统最终输出
- 双人独立标注
- 自动比较分歧
- 第三人仲裁
- 冻结后生成版本号和哈希

**标注质量指标**
记录：
- 字段一致率
- 证据区间一致率
- 分歧数量
- 仲裁比例
- 标注规范版本

### 10.5 评测指标体系

#### 抽取质量指标
- 字段 Precision
- 字段 Recall
- 字段 F1（单值和多值分别统计）
- 无依据输出率
- 空值误报率

#### 证据质量指标
- 证据检出率
- 证据精确率
- 证据边界字符区间 IoU

**证据 IoU 规则**：
- 人工标注允许多个合法证据区间（`acceptable_evidence_spans[]`）
- 系统证据只要与任一合法区间满足要求，即判为正确
- 边界 IoU 为辅助诊断指标，系统返回稍长上下文仍视为有效证据

#### 可信输出质量指标
- 高可信字段准确率
- 高可信字段覆盖率
- 低可信过滤准确率
- 正确字段误杀率

#### 来源谱系质量指标
- 转载识别 Precision
- 转载识别 Recall
- 独立来源误判率

### 10.6 主指标与诊断指标

**正式主指标**（在完整测试集上报告并计算置信区间）：
- 高可信字段准确率
- 高可信字段覆盖率
- 无依据输出率（相对下降 + 绝对百分点变化）
- 证据精确率
- 转载识别精确率

**诊断指标**（用于错误分析，不作过强结论）：
- 不同字段 F1
- 不同公告类型表现
- 不同来源表现
- 不同行业表现
- 不同支持度类别表现

### 10.7 输出策略工作点

由于 BidAgent 不使用单一总置信度分数，因此不宣称生成连续的 Precision-Coverage 曲线。

系统报告不同输出策略下的 Precision-Coverage 工作点：

| 策略 | 输出范围 |
|---|---|
| 严格策略 | 仅输出 high |
| 默认策略 | 输出 high 和满足指定条件的 review |
| 宽松策略 | 输出 high 与全部 review |
| 审计策略 | 展示所有字段，包括 low |

通过不同工作点说明准确率与覆盖率之间的权衡。

### 10.8 消融实验设计

设置四组对比，量化每个模块的实际贡献：

| 实验组 | 配置 |
|---|---|
| **A：Direct LLM** | 直接输出字段，无证据要求 |
| **B：LLM + 候选证据** | 要求模型同时给出证据文本，但不做程序验证 |
| **C：LLM + 程序证据验证** | 验证证据存在性和字段等价性，做确定性字段校验 |
| **D：完整 BidAgent** | 证据验证 + 来源处理 + 版本/冲突处理 + 选择性输出 |

**可回答的问题**：
- 仅让模型返回证据是否有效
- 程序验证降低了多少无依据输出
- 来源和版本处理解决了多少字段冲突
- 选择性输出牺牲了多少覆盖率

### 10.9 成本与性能指标

可信管道可能调用更多步骤，需同时报告成本开销：

| 指标 | 说明 |
|---|---|
| 单篇平均 LLM 调用次数 | 主抽取 + 重试 |
| 平均输入 Token | 每篇公告 |
| 平均输出 Token | 每篇公告 |
| 平均处理时间 | 端到端 |
| P95 处理时间 | 端到端 |
| 单篇估算成本 | 基于当前模型定价 |
| 失败重试率 | LLM 调用失败重试比例 |

### 10.10 置信区间

Bootstrap 以采购项目为最小重采样单元：
- 同一项目的公告、版本和字段整体参与采样
- 不按单个字段独立采样
- 报告关键指标的 95% 置信区间
- 记录随机种子和采样次数

### 10.11 Baseline 公平性

Baseline 与 BidAgent 使用：
- 相同底层模型
- 相同公告文本
- 相同字段定义
- 相同提示词主体
- 相同温度和采样参数
- 相同重试次数
- 相同 JSON Schema
- 相同测试集

主要变量为：
- 是否验证证据
- 是否进行确定性字段校验
- 是否处理来源角色
- 是否识别转载谱系
- 是否进行版本和冲突处理
- 是否采用选择性输出

### 10.12 实验复现信息

每次实验保存：
- 模型角色（主控/抽取/基线）
- 模型服务商
- 模型完整标识
- 模型快照或 API 版本
- 请求时间
- temperature
- top_p
- seed（如支持）
- request_id
- prompt_hash
- response_hash
- normalizer_version
- evidence_rule_version
- display_rule_version
- 数据集版本和哈希
- 代码提交版本

### 10.13 MVP 验收目标

建议目标为：
- 高可信字段覆盖率不低于 60%
- 高可信字段准确率不低于 95%
- 高可信准确率 95% 置信区间下限不低于 92%
- 相比 Direct LLM Baseline，**无依据输出率相对下降不低于 50%**，并同时报告绝对百分点变化
- 证据精确率不低于 95%
- 转载识别精确率不低于 90%

以上均为目标，不得在实际测试前作为已实现结果宣传。

最终材料必须填写真实数据，未达到目标时如实报告并进行错误分析。

### 10.14 测试集纪律

- 测试集不得提供给参与提示词和规则优化的模型
- 开发和校准阶段不触碰测试集
- 第四周冻结代码和规则后才运行最终测试
- 测试结果不用于本轮代码优化
- 仅非算法性故障可申请重跑并记录原因

- 点击字段高亮清洗后原始文本中的证据
- 展开查看全部关联证据（主证据、限定条件、上下文）
- 展开查看抽取支持度
- 查看来源类型和页面发布角色
- 查看转载谱系
- 查看公告版本变化
- 查看事实冲突原因
- 对比直接 LLM 输出和 BidAgent 输出
- 展示被拒绝的无依据字段

### 11.3 三分钟 Demo 流程

**核心叙事：官方原始来源 + 直接证据 + 程序验证 = 高可信**

**0～15 秒：问题提出**
> AI 可以快速抽取招投标公告，但尽调人员如何确认金额和企业名称不是模型编出来的？

**15～45 秒：查询与去重**
- 搜索某供应商
- 展示两个官方来源
- 展示同源转载识别
- 展示公告列表

**45～90 秒：证据验证（核心亮点）**
- 点击中标金额
- 高亮原文主证据
- 展开多段证据（主证据 + 分包限定）
- 说明：LLM 只提供候选，程序负责在快照中搜索验证

**90～120 秒：拒绝与冲突**
- 展示一个无证据字段被系统拒绝的案例
- 展示一个版本差异案例（更正公告更新了金额）
- 展示一个事实冲突进入人工复核的案例

**120～150 秒：组织实体观察信号**
- 展示公开中标活跃度
- 展示公开中标集中度
- 展示数据范围和完整性说明

**150～170 秒：评测结果**
- 展示独立测试集结果
- 展示 Baseline 对比和消融实验结论
- 展示成本开销

**170～180 秒：总结**
- 回到核心定位：将不可核验的 LLM 输出转化为可复核、可追踪的数据资产

**注**：独立交叉验证作为额外增强案例展示，不作为典型常态强调。

## 十三、安全与数据治理

### 13.1 安全重点

**SSRF**
- 仅允许 HTTP/HTTPS
- 检查 IP 字面量
- 校验 DNS 解析结果
- 拦截内网、回环、链路本地和云元数据地址
- 重定向后重新检查
- 限制端口、超时和响应体大小
- 必要时使用隔离下载服务

**路径安全**
- 使用白名单存储目录
- 使用真实路径校验
- 禁止路径穿越
- 文件名与真实存储键分离

**凭证安全**
- API Key 使用高熵随机值
- 服务端只保存基于服务端密钥的 HMAC 摘要
- 密码使用 Argon2id
- Cookie 使用 AES-GCM
- 加密密钥通过环境密钥或密钥管理服务提供
- nonce 必须唯一
- 日志不得记录凭证

### 13.2 数据开源边界

| 内容 | 开源策略 |
|---|---|
| 核心代码 | 开源 |
| 评测框架 | 开源 |
| 标注规范 | 开源 |
| 数据模型和 API 文档 | 开源 |
| 少量合法公开样例 | 可开源 |
| URL 和结构化标注 | 根据来源规则发布 |
| 政府公告全文快照 | 依据具体来源规则决定 |
| 商业平台全文 | 默认不发布 |
| 用户 Cookie 和凭证 | 绝不发布 |

### 13.3 数据删除

支持按以下范围处理删除：
- 来源 URL
- 来源平台
- 公告来源实例
- 页面快照
- 用户授权数据

删除操作应记录：
- 请求依据
- 操作人
- 删除范围
- 执行时间
- 审计记录

## 十五、三模型协作方案

### 15.1 主控模型

负责：
- 项目架构与任务拆解
- 数据模型、API 和评测方案设计
- 为 GLM 5.2 与豆包 Turbo 制定输入上下文和验收标准
- 跨模块接口审查
- 代码、测试、文档和比赛材料的最终整合
- 识别不同模型输出之间的冲突并组织修正

总体规划不绑定主控模型的公开产品名称。实际使用的供应商、模型标识、API 版本和请求时间在实验记录中保存。

### 15.2 GLM 5.2

主要负责：
- 后端数据模型与数据库迁移
- 字段抽取及确定性验证算法
- 原始文本与规范化文本偏移映射
- 来源谱系和转载候选识别
- 事实断言和跨源比较
- 评测脚本
- 单元测试与集成测试

### 15.3 豆包 Turbo

主要负责：
- Web Demo 页面
- 字段证据高亮
- 来源谱系和版本历史展示
- 组织实体公开活动画像
- 评测图表
- UI 文案、README、PPT 和演示脚本初稿
- 产品流程与文档一致性检查

### 15.4 协作原则

1. AI 生成内容必须经过自动测试和人工确认后方可合入
2. 模型交叉审查不能替代人工代码审查
3. 多个模型不得同时无边界修改同一核心文件
4. 每项任务必须明确输入、输出、接口、禁止修改范围和验收标准
5. **测试集不得提供给参与提示词和规则优化的模型**
6. 所有实验记录真实模型标识、参数、数据版本和代码提交版本
7. 不以模型名称作为项目技术壁垒，核心壁垒是证据验证、来源谱系和独立评测

### 15.5 协作流程

```
主控模型定义任务和验收标准
    ↓
GLM 5.2 / 豆包 Turbo 分模块产出
    ↓
另一模型交叉审查
    ↓
主控模型进行接口、逻辑和文档整合
    ↓
自动测试与人工验证
    ↓
合并代码
```

## 十七、质量门禁

### 17.1 代码质量

- 核心公开函数具有类型注解
- 核心类和函数具有 docstring
- 禁止裸 except
- 禁止在生产业务逻辑中使用 print
- 配置不得硬编码
- 数据库迁移可追踪
- 核心算法单元测试覆盖率不低于 80%

### 17.2 数据质量

- 原始值不得因规范化而丢失
- 历史版本不得被新版本覆盖
- 无证据字段不得进入高可信
- 同一字段必须绑定明确公告版本
- 所有展示等级必须记录规则版本
- 测试集必须记录数据版本和哈希
- 多值字段不得强行压平丢失信息

### 17.3 性能目标

性能指标按文本长度分层，不使用单一不现实目标：

| 文本规模 | 证据验证目标（不含 LLM） |
|---|---|
| 小于 20 KB | P95 不超过 200 ms |
| 20～100 KB | P95 不超过 500 ms |
| 大于 100 KB | 单独记录，不作为 MVP 硬门禁 |

性能测试必须说明：
- 硬件环境
- 文本长度
- 字段数量
- 并发量
- 是否命中缓存

## 十八、比赛叙事

### 18.1 电梯 Pitch

供应链金融做供应商尽调时，真正的问题不是搜不到招投标信息，而是不敢直接相信 AI 抽取的结果。BidAgent 不依赖模型自报置信度，而是为金额、企业名称和项目编号绑定经过程序验证的原文证据，并区分公告来源、转载谱系和历史版本。用户可以从结构化字段一键回到抽取时的原始文本，使招投标信息从普通搜索结果转化为可复核、可追踪的数据资产。

### 18.2 亮点顺序

1. LLM 输出可能缺少依据，直接用于尽调有风险
2. BidAgent 为每个字段绑定可验证的原文证据（支持多段）
3. 程序而不是模型确认最终证据
4. 来源、转载和版本被明确区分
5. 独立测试集和消融实验证明无依据输出下降
6. 组织实体公开活动信号用于尽调辅助

### 18.3 高频问题

**和招投标搜索平台有什么不同？**

招投标搜索平台主要解决信息覆盖和检索问题；BidAgent 主要解决结构化字段是否有原文依据、来源是否明确以及数据是否可追踪的问题。

**可信度是否只是人工规则？**

系统不依赖单一主观分数。抽取支持度、来源质量和交叉验证状态分别保存，展示规则在校准集上确定，并使用独立测试集验证实际准确率和覆盖率。

**证据会不会也是模型编的？**

不会直接采信。LLM 只提供候选证据文本，最终证据必须由程序在指定公告版本快照中搜索并验证，找不到就标记为无证据。

**为什么不做信用评分？**

公开招投标数据不足以代表企业整体信用。BidAgent 只输出有明确数据口径的公开活动观察信号，不构成授信或投资依据。

**为什么很多公告没有独立交叉验证？**

同一业务公告通常只有一个原始发布主体，其他页面可能只是转载。单一官方原始来源加直接原文证据可以构成高可信，独立来源验证属于额外增强项。

**数据采集是否合规？**

MVP 优先处理无需登录的官方公开数据，检查平台规则并控制访问频率。商业平台仅在服务条款、接口协议或其他授权依据允许时接入，不绕过验证码、付费墙或技术限制。

## 十九、免责声明

BidAgent 的输出基于系统当前覆盖来源、时间范围和可访问的公开公告。系统可能存在数据遗漏、实体消歧错误、页面变更和抽取错误。所有公开活动观察信号仅用于辅助信息整理和人工尽调，不代表企业整体信用状况，不构成授信、投资、采购或合作决策依据。

## 二十、已知限制

- MVP 仅覆盖两个已冻结的官方来源适配器（ccgp + ggzy_national），不包含全部地方平台
- 地方公共资源交易页面结构差异较大，需逐个适配
- 部分公告正文可能依赖附件，附件仅下载不深度解析
- PDF、扫描件和复杂表格暂不保证完整解析
- 无统一社会信用代码时，企业消歧可能存在歧义
- 独立来源交叉验证在现实数据中可能较少，属于增强项非常态
- 100～110 篇测试集（约 70+ 项目）只能支持总体主指标，无法支撑大量细分结论
- 关键事实列表具有一定主观性，不纳入 MVP 核心验收
- SQLite 仅用于单实例 Demo
- 公开招投标数据不能代表企业完整经营和信用情况
