### 性能 A/B 第三轮：同轮交替 + 顺序翻转（**最终结论，以这一轮为准**）

再做一轮的原因：第二轮留了个 44% 的未解释尾巴（改前代码老进程 25.97 vs 冷进程 18.07）。
在动手查之前先排掉两个「测量工具/进程状态本身有问题」的假设，用了新脚本
`_perf/harness_overhead.py`（同时采客户端与服务端进程 CPU、线程数、RSS）。

**Q1 客户端是不是瓶颈（GIL 下 10 个 Python 线程串行）？⇒ 否掉**

```
并发 1   客户端 0.10 核   服务端 0.60 核
并发 10  客户端 0.09 核   服务端 4.39 核
```

客户端连 0.11 核都没到。「压测工具卡住并发档位」这个解释不成立。

**Q2 服务端是「进程没热」吗（aiosqlite 线程池 / 页缓存）？⇒ 否掉**

同一冷进程连续 5 轮不重启（并发 10，每轮 30s）：

```
轮1 47.7 → 轮2 50.0 → 轮3 49.0 → 轮4 43.4 → 轮5 44.6   （首轮就是高点，-6.6%）
线程数 20 → 17 → 14（线程池随空闲收缩，与吞吐无关）
```

**没有预热爬升**。

**Q3 那 44%？⇒ 只能归到「机器整体状态漂移」，两边同向。**

同一份新代码，并发 10 在三次实验里分别是 35.07 / 33.27 / 39.00，单独跑（无对照进程）时
甚至测到 **47.7~50.0**。⇒ **绝对 RPS 跨次可差 48%，一句都不能单独引用。**

**正式实验设计**：8017 = `d721fcc` 旧代码（`list_tenders` 内 2 段 `await db.execute`，grep 确认），
8016 = W3A+W3B（1 段），库同源 `sha256 704d1407a76d317f…`，
两进程同批次冷启动，**顺序每轮翻转**（第 1 轮旧→新，第 2 轮新→旧…），抵消顺序与时间双偏差。

| 并发 | 旧代码 5 轮 | 均值±σ | 新代码 5 轮 | 均值±σ |
|---|---|---|---|---|
| 1 | 29.7 / 23.7 / 33.5 / 26.3 / 33.3 | 29.30 ± 3.85 | 35.6 / 34.5 / 35.8 / 35.5 / 40.8 | **36.44 ± 2.23** |
| 10 | 18.7 / 15.0 / 19.1 / 26.1 / 26.9 | 21.16 ± 4.60 | 35.2 / 33.6 / 34.6 / 42.3 / 49.3 | **39.00 ± 6.00** |

```
并发 1 : 29.3 → 36.4 = +24.4%   1.61σ   1σ 区间 [25.45,33.15] vs [34.21,38.67] 不重叠
并发 10: 21.2 → 39.0 = +84.3%   2.36σ   1σ 区间 [16.56,25.76] vs [33.00,45.00] 不重叠
```

**比 RPS 更稳的指标：每请求 CPU**（`进程 CPU 核 ÷ RPS`，比值，能抵消环境漂移）：

```
并发 1 : 22.9 ms/请求  →  14.1 ms/请求   (-38.3%)
并发 10: 188.9 ms/请求 → 111.3 ms/请求   (-41.1%)
```

⇒ 两个档位独立算出 38% / 41%，互相印证。**这是本轮最硬的一条。**

| 并发 | 旧 变异系数 | 新 变异系数 |
|---|---|---|
| 1 | 13.1% | **6.1%** |

### 结论强度（按标准 24.3 的 σ 规则，以第三轮为准）

- **「每请求 CPU 降 38%~41%」：已证实**
  - 并发 1 −38.3%、并发 10 −41.1%，两个档位独立算出、方向与量级一致。
  - 这是比值指标，不受机器状态漂移影响，**是本轮最硬的一条**。
- **「W3A + W3B 合计相对改前（同轮交替，顺序翻转）」：已证实**
  - 并发 10：**+84.3%**，**2.36σ**，1σ 区间与 min-max 均完全不重叠。
  - 并发 1：**+24.4%**，1.61σ，区间不重叠但**只差 1.0**（旧最高 33.5 vs 新最低 34.5）⇒
    **已证实但边缘**，对外建议说「约 +24%」而非「+24.4%」。
- **「旧代码更抖（变异系数 13.1%/21.7% → 6.1%/15.4%）」：倾向**
  - 方向明确、两次都成立，但**没有做调度延迟采样，缺机理证据**。
- **「W3B 单独贡献 +10.4%」：仅倾向**（W3A 当时 32.87 是另一个进程、另一个时刻测的）
- **绝对 RPS 一律不引用**：同一份新代码在四次测量里并发 10 分别是
  35.07 / 33.27 / 39.00 / 47.7，**跨次差 48%**。

**能对外说的**：同一个 186.6 KB 列表接口，同轮交替对照下——
- **峰值容量（并发 3）从 40.2 提到 73.5 RPS，+83%，而服务端 CPU 几乎不变（1.47 → 1.48 核）**；
- 并发 1 从 29.3 提到 36.4 RPS（约 +24%）；并发 10 从 21.2 提到 39.0 RPS（+84%）；
- **每请求 CPU 从 22.9ms 降到 14.1ms（−38%）**；响应逐字节不变（`b76fd96c…`）。

**不能说的**：任何绝对 RPS 数字（跨次差 48%）；任何「生产环境提升 X%」（只在本机回环、单进程下验证）；
任何「高并发也能用」——并发 50/100 下 P50 是 1.6~5.8 秒，只能说「崩得更晚」。

## 已知限制

1. **解包顺序与 `select(...)` 列顺序强耦合**。将来往 select 里加列必须同步改解包，
   否则该端点直接 500（`ValueError: too many values to unpack`）。
   这是有意的取舍：换来每次请求约 2.3ms。守卫是 3 条等价测试。
2. **W3B 单独贡献只是倾向**（跨时间比较），对外只能说「W3A+W3B 合计比改前**约 +24%（并发 1）**」。
   （原文写 29%，是第二轮口径；第三轮同轮交替实测 29.30 → 36.44 = +24.4%，此处已更正。）

## 补跑 T3 完整阶梯（交付后追加，2026-11-07 晚）

`_perf/README.md` 定义了 T3「并发 1→10→50→100 找拐点」，但此前只跑过 1 和 10 两档。
本次补齐 7 档（8018 旧 / 8019 新，同批次冷启动，库同源 `704d1407…`，每档 60s）：

| 并发 | 旧 RPS | 新 RPS |
|---|---|---|
| 1 | 27.1 | 35.4 |
| 2 | 40.6 | 66.2 |
| **3** | **42.4（峰值）** | **71.3（峰值）** |
| 5 | 31.2 | 61.8 |
| 10 | 19.2 | 34.7 |
| 50 | 15.8 | 29.1 |
| 100 | 17.2 | 30.7 |

（此表为顺序跑，只看曲线形状；绝对数不作结论。）

**两条结论**：

1. **拐点在并发 3**，不是 1 也不是 5。并发 1 的 RPS 只是 `1/P50`，是单用户视角、不是容量；
   1→2 吞吐涨 50% 说明服务端能并行吃 2~3 个请求。**这修正了 `_perf/README.md` §3 原有的判断。**
2. **优化提高的是容量，不是并发扩展性** —— 新旧峰值都落在并发 3，瓶颈结构没变
   （单进程 uvicorn + GIL + aiosqlite 线程池），只是每个请求更便宜了。

**交替复测峰值（并发 3，顺序翻转，各 3 轮 ×30s）**：

| | 旧 | 新 | 变化 |
|---|---|---|---|
| 均值±σ | 40.17 ± 0.66 | **73.53 ± 1.85** | **+83.0%**（17σ，区间不重叠） |
| 服务端 CPU | 1.47 核 | **1.48 核** | 几乎相同 |
| 每请求 CPU | 36.6 ms | **20.1 ms** | **−45%** |

🔴 最值得对外说的一句：**同样的 CPU（1.47 vs 1.48 核），做出了 83% 更多的吞吐。**

**未解释（未证实）**：并发 5→10 两边同时腰斩（旧 −38%、新 −44%），
说明是结构性瓶颈而非本次改动引入；原因未查清，不许当结论引用。
