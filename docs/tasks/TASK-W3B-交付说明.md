### 性能 A/B 第二轮：冷进程对冷进程（受控实验，**这一轮才算数**）

改前代码用 `git worktree add C:/tmp/bidagent_pre d721fcc` 检出到独立目录，
与当前分支**同时**起服务（8014 / 8015），两份 `data/bidagent.db` 是同源同 sha256 的副本
（`704d1407a76d317f…`）。两个进程**同批次启动、同时热、交替打**。

| 并发 | 8014 改前（冷） | 8015 W3A+W3B（冷） | 变化 | 区间是否重叠 |
|---|---|---|---|---|
| 1（3 轮 ×20s） | 29.1 / 27.3 / 26.5（均值 27.63） | 35.4 / 36.3 / 36.2（均值 **35.97**） | **+30.2%** | 不重叠（29.1 < 35.4） |
| 10（3 轮 ×20s） | 18.1 / 17.8 / 18.3（均值 18.07） | 35.4 / 30.1 / 34.3（均值 **33.27**） | **+84.1%** | 不重叠（18.3 < 30.1） |
| 10（另一批 5 轮 ×15s，复现） | 19.4 / 19.1 / 19.5 / 19.1 / 17.5（均值 18.92） | 30.9 / 27.9 / 30.6 / 28.9 / 35.6（均值 **30.78**） | **+62.7%** | 不重叠（19.5 < 27.9） |

**并发 10 两批共 8 轮合并**：改前区间 17.5–19.5（均值 18.60），改后区间 27.9–35.6（均值 31.71）
⇒ **+70.5%，两批各自都完全不重叠**。

⇒ 并发 1 的点估计非常稳（第一轮 +29.2%、第二轮 +30.2%）；
并发 10 的点估计不稳（+62.7% ~ +84.1%），**只报区间，不报单一倍数**。

**逐字节等价在冷进程对冷进程下再验一次**：

```

port 8015 http=200 bytes=191064    (W3A+W3B，一条 JOIN)
b76fd96c409ce023d3bf73b0a760a4ddd21010c4aafe99a3e300085b328ac59d  两者相同
```

⇒ 两个**不同 commit、不同进程**产出的 829 条 / 191064 字节完全相同。

### 🔴 第二轮暴露的一个未解释现象

同一个改前代码，**跑了三天的老进程在并发 10 下有 25.97 RPS，刚起的冷进程只有 18.07**，
差 44%。这解释了为什么第一轮只测出 +35%、第二轮测出 +70%：
混杂因素的方向是**压低**了新代码的优势，不是抬高。

但「老进程在高并发下更快」这个现象**本身没有查清**（可能与 SQLite 页缓存驻留、
堆碎片分布、或三天里积累的其它进程状态有关）。**如实登记为未解释，不许当结论引用。**

⇒ 这也是本轮最大的方法论教训：**跨进程比吞吐，必须同批次冷启动；否则噪声可达 40%+。**

延迟（同一轮采样）：

| 并发 | 改前 P50 / P95 | 改后 P50 / P95 |
|---|---|---|
| 1 | 32–42 / 45–53 ms | **30–31 / 36–37 ms** |
| 10 | 315–489 / 413–650 ms | **279–283 / 344–349 ms** |

### 结论强度（按标准 24.3 的 σ 规则）

- **「W3A + W3B 合计相对改前（冷进程对冷进程）」：已证实**
  - 并发 1：**+30.2%**，两轮独立实验分别是 +29.2% / +30.2%，区间均不重叠 ⇒ 点估计稳定
  - 并发 10：**+63% ~ +84%**（8 轮合并 +70.5%），两批各自区间不重叠 ⇒
    方向与量级确定，**但点估计不稳，对外只报区间**
- **「W3B 单独贡献」：仅倾向**
  - W3A 当时并发 1 实测 32.87 → 本次 36.30，**+10.4%**；
    探针预测 2.27ms / 19.62ms = **11.6%**，两者一致。
  - 但 32.87 是**今天早些时候、另一个进程（8012）**测的，不是同轮交替 ⇒
    跨时间比较，按 24.3 只能标「倾向」。
- **「第一轮那组 +29.2% / +35.0%」：作废为方向性证据**，原因是进程年龄混杂（见上文）。

**能对外说的**：同一个 190KB 列表接口，受控条件下并发 1 从 27.6 RPS 提到 36.0 RPS（+30%），
并发 10 从 18.6 RPS 提到 31.7 RPS，响应逐字节不变。
**不能说的**：「高并发提升 70%」是个区间中位数，且只在本机回环成立，没有跨机器证据。

## 已知限制

1. **解包顺序与 `select(...)` 列顺序强耦合**。将来往 select 里加列必须同步改解包，
   否则该端点直接 500（`ValueError: too many values to unpack`）。
   这是有意的取舍：换来每次请求约 2.3ms。守卫是 3 条等价测试。
2. **W3B 单独贡献只是倾向**（跨时间比较），对外只能说「W3A+W3B 合计比改前快 29%（并发 1）」。
3. **残余约 3.6ms 未定位**：残差 12.47ms − 框架 3.76ms − 拼装 3.67ms ≈ 3.6ms，
   分散在 `@app.middleware("http")`（BaseHTTPMiddleware，每请求起一个任务）+ SlowAPI 中间件上。
   非单点，动中间件的风险远大于收益，本轮明确不做。
4. **改前那 28.10 RPS 的三轮波动很大**（24.9–30.3），说明本机负载本身不稳；
   所以这里的结论只用「区间是否重叠」判，不用均值差硬算倍数。
5. **未在 CI 上跑过**（分支未推），仅本机 Windows + Python 3.13 验证。
6. **「老进程比冷进程快 44%」这个现象没有解释**。同一个改前代码，跑了三天的 8011 在并发 10
   有 25.97 RPS，冷启动的 8014 只有 18.07。可能与 SQLite 页缓存驻留 / 堆分布有关，**未证实**。
   它带来的后果是：任何「跨进程、不同时刻」的吞吐对比都会带 ±40% 的系统偏差，
   本轮因此只认「同批次冷启动 + 交替」的实验。
7. **并发 10 的改后点估计在 27.9 ~ 35.6 之间漂**（8 轮），比改前的 17.5 ~ 19.5 离散得多。
   说明新代码在高并发下更接近饱和边界；这不是噪声问题，是需要后续查的真问题，本轮不动。
